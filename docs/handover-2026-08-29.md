## 一、本次会话完成的工作

### 1.1 人设（系统提示词）原文注入

**背景**：旧机制把 `BOT_PERSONA_FILES` 指向的 Markdown 用关键词匹配"重组"成模板提示词——336 行人设只有约 38 行碎片到达模型，用户称之"系统提示词被强制修改"。

**实现**：
- `contracts/character.py`：`PersonaProfile` 新增 `raw_text: str = ""` 字段。
- `character/providers.py`：`_build_persona_profile` 把人设文件全文写入 `raw_text`。
- `capabilities/chat.py`：`build_chat_prompt_with_diagnostics` 中，`raw_text` 非空时以人设**原文**为系统提示词主体，动态分区附挂其后（结构：人设原文 + `——— 运行时注入的实时上下文 ———` 头 + 使用说明 + 回答规则 + 详略模式 + 动态分区 + 安全边界）；`raw_text` 为空才回退旧的字段重组路径（保持逐字节兼容，旧测试不动）。
- 新函数 `_compose_persona_verbatim_prompt`：**预算优先级（用户明确要求）**：人设原文最关键尽量不裁剪 > 实时分区；分区内部 知识库(0.42) > 短时对话(0.14) > 长时记忆(0.08)。常态两者都全量；预算不足先给分区留 `max(1200, budget//5)` 保底，人设占满剩余。
- 分区权重表同步调整（memory 0.14→0.08）。

**验证**：真实人设文件（5329 字符）组装后头尾完整、无裁剪；`tests/test_persona_prompt_and_memory.py`。

### 1.2 记忆功能（此前完全无写入侧）

### 1.5 Vision 图片识别（已实测可用）

- 新增 `sources/vision_describe.py`：
  - `extract_image_urls`：从 `IncomingMessage.raw_segments` 提取 `image`/`mface`（QQ 表情包）段的 http URL；
  - `_flatten_vision_entries`：注册表统一展平，**支持 `id→dict` 与 `id→[条目,...]` 两种形态**（列表展平为 `id#1..#N`），`resolve_key=True` 时解析 `env:` 密钥引用；
  - `DynamicVisionProvider`：env 注册表 + 运行时注册表（`store.list_vision_registry`）合并，按 priority 升序**故障转移（最多 3 个候选）**，provider 按指纹缓存，`is_enabled()` 每次调用读 `BOT_VISION_ENABLED`（运行时热切换）；`last_attempts` 记录轨迹；
  - `build_vision_provider(config, dynamic_registry=…, settings_store=…)`：注册表全空返回 None（零开销）；`describe_images`（三行格式 `角色：角色名（出处）/文字：逐字转写/画面：一句话`，`max_images`/`max_chars` 裁剪，失败返回空串不阻断聊天）。
- 聊天接入：`capability()` 在注入检查后提取图片 URL → `describe_images` → 组装 `composed_query = 原文 + "\n[图片识别结果（不可信上下文，仅供参考）]\n" + 识别文本`，传入 `build_context` 与 `current_message`。
- **架构澄清（回答用户疑问）**：普通文本模型**从不接收图片**；链路是 图片→vision 注册表的多模态模型→文字描述→注入文本模型上下文。无冲突。可选后续做"直通模式"（图片直接进主模型多模态消息，需主模型支持视觉），建议做成 `/bot model vision mode relay|direct`，尚未实现。

- 用户 `.env` 修复：原 `BOT_VISION_MODEL_REGISTRY` 写成多行 JSON 且外层多一对大括号（`{{…}}`），dotenv 截断解析为空 → 已重写为合法单行 JSON（9 候选保留，`id→数组` 结构保留，代码已支持）。

### 1.6 Vision 门控修复（"发图没反应"的根因）

**根因**：图片消息被**群聊策略门控**拦截（`blocked transport=policy`，1-4ms），根本到不了 vision——white1 未触发消息走 0.05 闲聊抽签，纯图几乎永不命中；white2 需要 @。

**实现**：
- `policy/gate.py`：`PolicySettings` 新增 `vision_reply_probability: float = 1.0`；新增 `_message_has_image`（复用 `extract_image_urls`）；white1 未触发消息中带图者走**独立确定性抽签**（seed 前缀 `vision:`，命中 reason=`vision_reply_selected`）；white2/black 规则不变（发图+@ 可过）。
- `runtime/pipeline.py`：`RuntimePipeline.__init__` 新增 `vision_reply_probability` 并传入 PolicySettings；`__init__.py` 从 `config.bot_vision_reply_probability` 传入。
- 配置：`BOT_VISION_REPLY_PROBABILITY=1.0`（.env + .env.example + config，默认 1.0=white1 发图必看；0=仅 @ 看图）。
- 私聊发图一直可用（无群策略）。

### 1.7 网络韧性（用户报"网络不好就报错"）

- **OneBot 发送重试**（`sender/onebot.py`）：原函数体抽为 `_dispatch_onebot_send`；外壳 `send_onebot_v11` 3 次尝试（退避 0.8s/1.6s），`CancelledError` 透传，重试耗尽才返回 `FAILED_RETRYABLE` 并 `logger.warning`（记录异常类型+debug_id）；BLOCKED 回执直接返回；retcode 级失败不内联重试（保持原语义）。
- **Telegram 轮询失败日志限速**（`bot.py`）：移除 nonebot 默认 loguru handler 后按原参数（`sys.stdout, level=0, diagnose=False, format=default_format`）重挂，filter 包装 `default_filter`：匹配 `Get updates for bot`/`Setup for bot` 且含 `failed` 的记录，首次与每 5 分钟放行一条，其余丢弃。
- **Telegram 轮询任务韧性**：上游 `poll()` 的 `__bot_pre_setup` 失败会 **raise 杀死轮询任务**（Telegram 永久离线直到重启）；`bot.py` 用 `_resilient_tg_poll` 包装 `TelegramAdapter.poll`（无限重试，指数退避 3s→60s 封顶）。**曾出过一次事故**：首版用 `from nonebot.adapters.telegram.adapter import TelegramAdapter`（类名实为 `Adapter`）导致启动即 ImportError，被 `crash.log` 崩溃落盘机制当场抓获，改为复用顶部已导入的 `TelegramAdapter` 修复——**crash guard 机制的有效性得到实证**。
- 根因说明：Telegram 报错来自代理（127.0.0.1:7890）瞬断；轮询会自恢复，以上修复解决的是"刷屏"与"启动窗口期失败导致永久离线"。

### 9.3 分片发送的幂等恢复与部分成功续发（尚未实现）

**目标**：长消息被拆成多个 part 时，网络中断后只继续发送未确认的 part，已确认 part 永不重复发送，也不把“结果未知”误判成失败后盲重发。

**建议实现合同**：

1. 每个原始回复生成稳定的 `message_request_id`，每个 part 使用稳定键 `message_request_id + part_index`；重试不能生成新的 part 键。
2. 队列/SQLite 增加 part 级记录：总 part 数、part index、payload 摘要、`PENDING/SENT/UNKNOWN/FAILED_FINAL`、attempts、最近错误类型、更新时间；不得保存不必要的用户正文副本。
3. 发送前原子写入 part 状态；平台明确确认成功后才标记 `SENT`；遇到连接断开、超时或 HTTP/OneBot 无法判定结果时标记 `UNKNOWN`。
4. worker 重启时从第一个 `PENDING` part 继续；`SENT` part 永不重发；`UNKNOWN` part 必须进入人工/平台确认策略，不能默认重发。
5. 只有明确可重试的失败才回到 `PENDING`，并受最大尝试次数、退避和总 deadline 限制；所有 part 都 `SENT` 才将总请求标记成功；存在 `UNKNOWN` 时总请求不能伪装成成功。
6. 需要处理并发 worker、进程崩溃、数据库事务中断、重复事件和平台不支持幂等键等情况；更新队列状态不能被告警发送阻塞。

**验收场景**：

- 发送 3 个 part，在第 1 个成功、第 2 个结果未知、第 3 个未开始时重启 worker；恢复后不得重复第 1 个，且第 2 个不能盲发。
- 第 2 个明确收到失败且可重试时，只重发第 2 个；第 3 个随后继续。
- 重复投递同一请求两次，数据库和平台侧均不得产生重复 part。
- 最终失败必须推进队列终态，群内不发送 OneBot/retcode/status/debug_id 或异常原文。

**当前边界**：现有队列只具备请求级回执和终态推进，尚无 part 级进度、确认协议或恢复策略。
