## 二、验收重点（从矩阵行拆解）

1. **脱敏**：故障包、补丁内容、诊断报告交付前全部脱敏；接触不到敏感原文的修复器只获得脱敏最小复现（扩展 §7.1:231）。
2. **两轮预算**：每故障最多 2 轮候选补丁，超预算 abandoned 并保留失败测试（RED）声明。
3. **保留失败测试**：禁止删测试、调低阈值、以任何形式掩错。
4. **越权部署拒绝**：自动应用/部署面一律拒绝并审计；**人工审核通过也不自动部署**——部署是独立的人工/具名授权动作（扩展 §7.2:243）。
5. **链路完整性**（本立项核心缺口）：补丁生成→待审队列→人工批准→应用，四段全通且每段有载体；现状只有中段（待审编排）有载体，见 §3.6。
6. 隐含：权限/证据不足就 blocked，不伪称自行修好（扩展 §7.1:231）。

## 四、立项方案要点

### 4.1 链路总图（本立项交付目标）

```
真实故障 → [S14 recovery] FailureKind.patch_required 分类上报
        → [G1 提案源桥] 脱敏故障包（复用 render redact 真身）→ RepairService.submit_failure
        → [既有 repair] 两轮预算内生成候选补丁 → 沙箱验证（SandboxCopyVerifier :427）
        → 待审队列（pending 目录 manifest+patch，既有）
        → [G3 人工消费] GET /repairs/{id} 列表+详情 → 管理员逐行审 diff
        → 人工批准（POST /repairs/{id}/review，只改状态、零写入目标）
        → 应用=人工执行（改码须重启生效铁律）；部署=用户授权动作
```

红线钉死：**任何一环都不存在机器自动写目标文件/自动部署的路径**；`apply_to_target`/`deploy_patch` 的 raise+审计锁永久保留（回归测试 :212/:235/:266 常驻门禁）。

### 4.2 提案源三候选形态（**需用户裁定**，见 §八.1）

- **a) 事件桥+人工登记补丁（最小起步，S 级）**：recovery `patch_required` 事件 → 生成脱敏故障包 → 建 OPEN ticket；补丁 diff 由管理员人工准备后经 `submit_failure` 统一走待审/沙箱验证/留痕面。机器只做编排，零生成智能。
- **b) 规则/模板生成器**：对已知故障族（如测试断言漂移）用确定性规则产候选 diff——可控但覆盖面窄。
- **c) LLM 辅助修复器（进阶）**：合同明确允许修复器存在，但「不可访问敏感原文的修复器只获得脱敏最小复现」（§7.1:231）；产物**永远只进 pending**，无人工批准零落库；修复器离线运行、不触生产库不触网。引入 LLM=新增不可控面，须用户显式批准。

### 4.3 人工消费入口设计要点（G3）

- REST：control_plane 下 `GET /repairs/{id}`（详情=list_tickets + request_application 聚合）、`POST /repairs/{id}/review`（状态迁移 review 记录；扩展 §7.2:243）。认证沿用控制面既有 loopback+Bearer 面。
- 命令：`/bot repairs show`（§7.2:243 原文点名），进 echo 帮助注册表——**实现后才进现行 help**（合同原话，不得预挂）。
- review 语义：批准≠部署。批准后 ticket 状态置「approved_pending_manual_apply」，应用由管理员人工执行并回填结果；驳回/超期 abandoned。

### 4.4 审计与幂等

- 审计：`RepairAuditSink` 协议 :358 已有，生产 sink 落点待接（可复用 incident 面/ops 审计——落点待定，unknown）。
- 幂等：重复提交零重复产物已有测试锁（:391）；G1 桥接后同 fingerprint 重复上报应落到同一 ticket（实施时补测试）。

## 五、建议落点

- **既有 repair 服务**：`domains/ops/repair/` **复用，不重建第二套**（矩阵 S0 批注「存量实现必须复用并补证据」）；13 测试引用面不动。
- **新缺口件（G1 桥/G3 入口）**：plan §8.3 G8:637 原建议「ops/ 新增 recovery/（与 monitor 同域）」——S14 席已把 recovery 域建成（三子包），因此建议桥接件落 `domains/ops/recovery/`（贴 patch_required 分类源），与 `domains/ops/repair/` 保持**单向依赖 recovery→repair**（repair 不反向 import recovery，防环）。两域是否合并为单一域=开放问题 §八.2（合并会动 13 测试引用面，默认不动）。

## 八、开放问题（需用户裁定）

1. **提案源形态三选一**（§4.2 a/b/c）：建议先 a（人工登记，S 级）跑通全链，b/c 后续按故障量再裁。

3. **REST/命令是否本轮接生产**：依赖接线波次与控制面在飞批；不接则 G3 仅有命令面方案。
4. **审批角色与保留期**：super_admin only？待审件（含 abandoned）保留多久/多大上限？
5. **「具名授权控制动作」边界**：扩展 §7.2:243 允许部署走具名授权控制动作，但 AGENTS.md 顶注要求代码补丁待审不自动部署——本立项书建议保守口径（应用与部署均人工），是否采纳。
