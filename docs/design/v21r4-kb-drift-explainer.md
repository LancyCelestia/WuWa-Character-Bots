# 知识库「kb_drift」是什么？——写给非技术读者的说明

> **一句话**：这是重启前体检的一项，查的是守岸人「翻书用的目录」和「书架上的书」数量对不对得上。现在对不上（目录卡 35341 张，原文只有 4611 段）。这事不紧急、不会弄坏机器人，但卡片柜确实积了灰，迟早值得收拾一次。

---

## 1. 它是什么

守岸人聊天时会翻自己的知识库——把收进来的资料切成小段，按意思相近程度找出来引用。这套查找分两层：

- **书（原文块，术语叫 chunks）**：资料被切成一小段一小段存进数据库，现在有 **4611** 段；
- **目录卡（向量索引，术语叫 ANN）**：每段文字配一张「检索卡」，按语义排好。查问题时先翻卡片，再按卡片取原文。

理想状态：一段原文，一张卡片，一一对应。`kb_drift` 就是数一数两边数量是否相等的体检项——它藏在重启前预检脚本里（`scripts/pre_restart_check.py` 第 5 项），**只读不改**：查之前先把数据库抄一份到临时目录再数，不碰正在运行的数据。

## 2. 现在的实际情况（已取证）

| 层 | 数量 |
|---|---|
| 目录卡（ANN 索引条目） | **35341** |
| 书（chunks 原文块） | **4611** |
| 其中已配好卡的原文 | 4539（另有 72 段还没配卡，这个小事系统会自动补，不用管） |

目录柜里有三万多张「废卡」——卡还挂在柜上，指向的原文早就不在了。数字来自生产库实测（`docs/design/v21r3-core-chain-audit.md` §五，2026-09-18 取证）。

## 3. 为什么会这样

三类常见来源，共同点是**目录只加不减**：

1. **整理过内容**：原文重新切块或删除后，数据库里的旧段落清掉了，索引里的旧卡却没人同步清走；
2. **换过嵌入模型**：做卡片的「分类方法」换过代，旧卡和新卡不是一套口径，全混在一个柜子里；
3. **清理不同步**：删原文和删索引是两步操作，中间哪次断掉了，就留下一批孤儿卡。

放着不管会怎样？查资料时先翻到废卡——轻则多花点查找时间，重则翻到内容对不上的段落，回答里引用的资料不够准。**日常聊天基本不受影响**：知识库只是守岸人回答时的参考材料之一，不是命根子。

## 4. 报了该怎么办

两个选项，选哪个都成立：

- **不管它**：机器人照常跑。代价是知识检索的质量和速度打点折扣，而且废卡越积越多，以后收拾起来更费劲。
- **重建索引**：把卡片柜清空，按现在的 4611 段原文重新做一整套卡。预检脚本给出的路径是三步一条链：**同步 → 补嵌 → 重建**。

**边界必须说清楚**：重建会重写 `ChatBot_Runtime/` 里的运行数据（索引文件、顺序表、数据库里的向量列）。这是线上实例的家底，按本项目铁律——**AI 不代改运行数据**。要不要重建、什么时候重建、重建前要不要先备份，由你自己决定、自己执行。

**动手前后的复查方式**：在工作区根目录跑一次

```
python scripts/pre_restart_check.py
```

看第 5 项 `kb_drift` 是否变绿（绿 = 两边数量相等）。重建后它显示 `ANN=4611 == chunks=4611` 就是收拾干净了。
