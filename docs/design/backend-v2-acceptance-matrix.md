## 证据记录格式

每行展开为叶执行卡后，证据至少保存：

```text
requirement_id / feature_id / scenario_id / run_id
source_commit（如有）/ dirty_tree_digest / manifest_revision
implementation_paths / assembly_paths
command / interpreter / environment_profile / fixture_version
started_at / finished_at / exit_code / actual_assertions
trace_ids / operation_ids / usage_attempt_ids / receipt_ids / artifact_ids
resource_peak / budget_used / cleanup_result
confidence / limitations / blocked_dependency / next_action
```

源码与运行证据分开。日志里的“success”必须有业务后置断言支持；不能靠返回200、存在文件或mock断言给真实平台标passed。文档链接检查属于文档交付证据，不属于上表业务功能通过证据。

## 覆盖维护与发布裁决

1. S0将每项拆到manifest叶节点，特别是LEGACY-001，逐个列已有业务，不能只测天气代表全插件。
2. 所有V21需求ID唯一且至少关联一个Scenario；跨多个阶段保留相同ID，追加证据，禁止复制出相互矛盾的状态行。
3. 每阶段更新四列和证据索引，并行继续（能用子代理就用子代理，依赖任务按序；限流为唯一上限），不等待重复授权。失败先根因复现，修后跑相关回归，最终全门禁实跑。
4. 本矩阵目标为完整交付，前端页面不在范围。未配置外部provider只可标协议实现、live blocked；不能宣称整机可发布。
5. 自动修复代码补丁待审；运行恢复与生产部署是不同权限。新接手AI不得把规划中的自动化权限当成本次已经获准的真实收件人、费用或部署窗口。
